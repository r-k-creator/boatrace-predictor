# 買い目提案システム 設計判断ログ

`scripts/generate_bets.py`(ランク・買い目決定)を中心に、なぜ今の設計になっているかを
記録するドキュメントです。「完成したらまとめる」のではなく、**変更するたびに追記していく
前提**のログです。数字やしきい値は今後のデータ蓄積で見直される可能性があります(見直した
場合もこのファイルを更新し、古い値を消さず「変更履歴」に残してください)。

関連: [README.md](../README.md)(システム全体)、[backtest_conclusion.md](backtest_conclusion.md)(モデルのパターン選定)

**運用ルール(2026-09-18追加)**: 複数の仮説がある調査を行う際は、調査結果だけでなく、
その後の議論を経てたどり着いた結論・判断理由もこのログに記録すること。「何が起きたか」
だけでなく「どういう議論を経て、なぜその結論に至ったか」を残すことで、後から見返した際に
判断の背景を追えるようにする。

## ランクしきい値(SS/S/A/B/C)

`predicted_probability`(推奨艇の予測勝率)に対するしきい値。`data/archive/backtest_evaluations_b.csv`
(504日ウォークフォワード検証、天候加法項パターン=本番モデル)の実測`hit_top1_rate`から
逆算した値で、勘で決めた数字ではありません。

| ランク | しきい値 | 実測的中率 | サンプル数 |
|---|---|---|---|
| SS | >= 0.80 | 86.2% | n=59(**薄いサンプル。95%信頼区間で±9pt程度、暫定値**) |
| S | [0.70, 0.80) | 77.7%(細分すると0.70-0.75/0.75-0.80ともほぼ同水準) | n=2,856(0.70-0.75: 2,291 / 0.75-0.80: 565) |
| A | [0.60, 0.70) | 67.9% | - |
| B | [0.50, 0.60) | 56.5% | - |
| C | < 0.50 | 41.3%(賭け対象外、参考表示のみ) | - |

**SSランクについて**: 2026-09-17時点でn=59という薄いサンプルに基づく暫定値です。Stage 2の
較正チェック(下記)を行う際は、SS帯の実測的中率を最優先で再検証し、Sランクとの差が
データ増加で縮まっていないか確認すること。差が縮まっていた場合は閾値の微調整だけでなく、
**SSという独立ランクを維持する妥当性自体**を再検討する(単に数字を動かすだけでは不十分)。

## 予算とベットタイプの組み合わせ

| ランク | 予算 | ベットタイプ | 配分ロジック |
|---|---|---|---|
| SS | 5,000円 | 2連単(安全側)+3連単(上振れ) | 同じ予算をエントロピーに応じて分割(SSはS予算を共有=点数を絞って攻める設計であり、予算を増やしているわけではない) |
| S | 5,000円 | 2連単(安全側)+3連単(上振れ) | 分割比 0.25〜0.60(レースの拮抗度で変動) |
| A | 3,000円 | 3連単(主)+(2連単 or 3連複) | 推奨艇の確率が0.65以上なら2連単寄り(S寄り)、未満なら3連複寄り(B寄り)。分割比0.20〜0.50 |
| B | 2,000円 | 3連複のみ | 分割なし、全額 |
| C | 0円 | なし | 賭け対象外(参考情報のみ) |

## 点数(組み合わせ数)ロジック

- S/A/B: 基本6〜9点(拮抗度に線形連動)、極端な混戦(拮抗度>=0.90)では最大15点まで拡張。
  下限を3点ではなく**6点**にしているのは明示的な要望による(「SS以外は最低でも6点」)。
- SS: 別ロジックで3〜5点(「点数を絞った、より攻めた買い目」という要望のため、あえて少なく)。

### 拮抗度(competitiveness)の算出方法 — 一度失敗して直した箇所

最初は6艇全体のシャノンエントロピーをそのまま使っていましたが、これは**本命艇の確率が
上がるほど機械的に下がる**性質があり、ランクが上がるほど(=本命の確率が高いほど)
実現しうるエントロピーの範囲自体が下にシフト・縮小することが判明しました
(中央値: Bランク0.73 → Aランク0.65 → Sランク0.53、実データ207レースで確認)。
これを固定の[6,9]という点数レンジにそのまま通していたため、実際にSランクの13レース中
12レースが同じ8点に固まってしまうという不具合が発生(ユーザー報告「買い目が4点のまま
に見える」の調査で発覚)。

**修正内容**: 本命艇を除いた残り5艇だけのエントロピー(`residual_entropy`、再正規化)に
変更。中央値はランクに依存しなくなった(B 0.878/A 0.886/S 0.877)一方、実現範囲(最小〜
最大)はまだランクごとに微妙にずれる(B[0.547,0.988]/A[0.689,0.981]/S[0.796,0.941])ため、
**ランクごとに別々の正規化レンジ**(`RESIDUAL_ENTROPY_RANGE_BY_RANK`)を適用しています。
最初は共通の1つのレンジで試しましたが、それでもSランクの点数クラスタリングは解消しな
かったため、ランク別レンジの採用に至りました。SSランクは実データがまだ無いため、Sの
レンジを暫定的に借用しています。

この一連の分析は2026-09-16・09-17の実データ(2日分)のみに基づく暫定的なものです。
データが増えたら再検証してください。

## reasons由来の注意フラグによるランク降格

`reasons`のいずれかに「要注意」「留意点」「食い違」のいずれかが含まれる場合、ランクを
1段階下げます(SS→S→A→B→C)。この3語は`git log -p`で過去の`candidates.json`全履歴を
確認し、実際に出現した警告語がこの3つだけだったことを根拠に選定しています。予算半減や
除外ではなく「ランク降格」を選んだのは、ベットタイプの組み合わせ(3連単中心か3連複中心か
など)にも正しく波及させるためです。降格した場合は`caution_flagged`と`rank_without_caution`
を記録し、透明性を保っています。

**未実装・将来案**: 上記3語で拾えない、より柔らかい注意喚起表現(「ただし」「一方で」
「懸念」など)を月1回程度、目視レビューできるレポートとして出す仕組み。今は不要、
必要になったら着手。

## 毎晩の収支精算パイプライン(Stage 1、2026-09-17実装)

`evening_results.yml`/`evening_results_retry.yml`が結果取得後に実行する順序:
`evaluate_candidates.py` → `generate_bets.py` → `evaluate_bets.py` → コミット → メール送信。

- `fetch_results.py`が2連単・3連単・3連複の払戻(`exacta_*`/`trifecta_*`/`trio_*`)を
  `data/archive/results_races.csv`に保存するよう拡張済み(過去77,940行は空カラムのまま、
  遡って再取得はしていない)。
- `evaluate_bets.py`が実際の買い目(`generate_bets.py`が生成したもの)を上記の払戻データと
  突き合わせて的中判定・回収額を計算し、`data/latest/bets_evaluations.csv`に1ベット=1行で蓄積。
  これがStage 2(下記)の分析対象データになる。
- **二重送信防止の重要な仕組み**: 夜間ジョブの中で`generate_bets.py`が`data/latest/candidates.json`
  をローカルに書き換えるが、`candidates_notify.yml`は「`data/latest/candidates.json`へのpush」を
  トリガーにしているため、これをそのままコミットすると朝の候補メールが深夜に再送されて
  しまう。そのため夜間ジョブのコミットステップでは必ず
  `git restore --staged data/latest/candidates.json`を実行してから`git diff --cached`を確認する。
- **「候補レース振り返り」メールは2026-09-18に送信停止**(「本日の収支」メールは継続)。
  `evaluate_candidates.py`自体(的中率・回収率の計算、`data/latest/candidates_evaluations.csv`
  への記録)はモデル精度追跡の診断データとして引き続き毎晩実行する。停止したのは
  `evening_results.yml`/`evening_results_retry.yml`の「Send candidate evaluation email」
  ステップ(メール送信)のみ。

## GitHub Actions スケジュール実行の落とし穴

- **push駆動の`candidates_notify.yml`は新規ブランチにワークフローを追加しただけでは動かない**
  (デフォルトブランチにマージされて初めて、その後のpushイベントで発火する)。
  `morning_program.yml`が初日動かなかった原因もこれ(バグではなく、その日の8:00 JSTの
  発火タイミングをマージが過ぎてから通り過ぎていただけ)。
- **`cron`の分を0にしていると、GitHub Actions側の混雑で数時間規模の遅延が起きうる**
  (GitHub公式ドキュメントが明記している既知の挙動)。2026-09-17、
  `evening_results.yml`(22:00 JST予定)と`evening_results_retry.yml`(23:00 JST予定)の
  初回実行がそれぞれ約4.5時間・4時間遅延したため、分を0以外(22:03 JST / 23:07 JST)に
  ずらして緩和した。他のワークフロー(`morning_program.yml`等)も同様に分=0のままなので、
  同じ遅延リスクが残っている(未対応、必要になったら同様に調整)。
- **GITHUB_TOKENによるpushは他のワークフローのpushトリガーを起動しない**(無限ループ防止の
  ための既知の制限)。`auto_merge_data_branches.yml`が`GITHUB_TOKEN`でmainへfast-forward
  pushしても、`candidates_notify.yml`(`data/latest/candidates.json`へのpushがトリガー)は
  自動発火しない。2026-09-18に、fast-forward成功直後に`gh workflow run candidates_notify.yml`
  /`gh workflow run candidates_insurance_check.yml`を明示的に呼ぶステップを追加して対応
  (candidates.jsonが変更ファイルに含まれる場合のみ)。ジョブの`permissions`に
  `actions: write`が必要。

## Sランク全賭けシミュレーション(2026-09-18実施)

過去データ(2025-05-01〜2026-09-17、backtest.pyのウォークフォワード検証)でS以上
(SS/S)ランク該当レース全てに本番と同じロジック(`generate_bets.py`のランク判定・
`build_bets`)で買い目を生成し、実際の払戻(2連単/3連単/3連複)と突き合わせた結果:

| 区分 | レース数 | 買い目数 | 投資 | 回収 | 収支 | 回収率 |
|---|---|---|---|---|---|---|
| 全体(SS+S) | 2,919 | 26,540 | 14,595,000円 | 11,276,010円 | -3,318,990円 | 77.3% |
| SSのみ | 59 | 257 | 295,000円 | 277,690円 | -17,310円 | 94.1% |
| Sのみ | 2,860 | 26,283 | 14,300,000円 | 10,998,320円 | -3,301,680円 | 76.9% |

買い目種類別: 2連単 回収率78.9%(13,301買い目)、3連単 回収率75.4%(13,239買い目)。

### 回収率77.3%の原因分解(2026-09-18、`scripts/analysis/analyze_s_rank_simulation.py`)

1. **的中率と回収率の分離**: レース単位の的中率(1点でも的中)は75.5%と高いが、買い目単位の
   的中率は12.3%、的中した買い目の平均払戻は100円あたり625円(6.25倍)と低い。
   予想精度不足というより「多点買いでレース単位の的中は確保できているが、その多くが
   1号艇絡みの堅い決着=低配当」という構造が主因。
2. **条件別の偏り**: 場別に63.2%〜97.6%、風速帯74.4%〜78.4%、波高帯69.8%〜85.4%と
   ばらつきはあるがサンプルが薄く系統的とは言えない。進入コース別では2,919レース中
   2,908件が1号艇(S/SS選定基準=予測確率0.70以上が必然的にコース1に偏るため)。
   特定条件だけが弱いのではなく、選定基準自体がコース1中心=堅い決着中心になる性質が
   支配的。
3. **点数基準の影響**: 旧基準(3〜10点)なら回収率77.5%、新基準(6〜9点)なら76.9%と
   0.6pt悪化。仮説(点数を増やすほど低確率・低配当の買い目まで拾い配当効率が下がる)の
   方向とは一致するが、影響は小さく77.3%全体の低さの主因ではない。

**結論**: 回収率の低さは点数設計よりも、S/SSランクの選定基準自体(予測確率0.70以上→
必然的に1号艇中心の堅い決着に偏る)に起因する。日本の公営競技の払戻率は制度上おおむね
75%前後が上限(控除率約25%)であることを踏まえると、77.3%はオッズを考慮しない均等買いの
結果としては制度上の上限に近い水準であり、これ以上の改善にはHarville確率の較正精度向上
(Stage 2)や選定基準自体の見直しが必要になる可能性がある。

### ベースライン比較(2026-09-18、`scripts/analysis/simulate_boat1_baseline.py`)

「S/SSランクの選定をせず、対象期間の全レースで単純に1号艇軸の2連単流し(1-2/1-3/1-4/
1-5/1-6の5点、モデル予測を使わない固定パターン)を、同じ1点あたり金額(500円)で
賭け続けた場合」との比較:

| 戦略 | レース数 | 投資 | 回収率 | レース単位的中率 |
|---|---|---|---|---|
| S/SSランク選定あり | 2,919 | 14,595,000円 | 77.3% | 75.5% |
| 1号艇軸2連単流し(選定無し) | 77,112 | 192,780,000円 | **76.2%** | 54.4% |

**回収率の差はわずか1.1pt**。S/SS選定は的中率を大きく引き上げる(54.4%→75.5%、
+21pt)ものの、回収率でみるとほぼ「毎回1号艇に賭け続ける」のと同水準にとどまる。
「絞り込んだ先も結局1号艇中心の堅い決着」という上記【2】の結論と整合しており、
**現状のモデルは的中率(1号艇が勝つかどうかの予測)は高いが、それが収益改善には
あまり結びついていない**ことを示す。Stage 2の較正チェックでは、的中率だけでなく
「選定の有無による回収率の差」も継続的に監視すべき指標として追加する価値がある。

**制約・注意点**:
- backtest.py側には実際のRoutineが付けていた`reasons`(要注意/留意点/食い違による
  ランク降格)が存在しないため、このシミュレーションには**caution降格が反映されていない**。
  実運用より強気(ランクが高め)の結果になっている可能性がある。
- オッズは一切考慮していない(このシステム全体の設計方針どおり)。回収率はあくまで
  「当たりやすさ」ベースの参考値であり、実際の期待値(オッズ込み)ではない。
- SS帯はn=59と依然薄いサンプル(SS閾値0.80の暫定性については[[project-boatrace-predictor-stage2-plan]]参照)。

**実装・再現方法**:
1. `scripts/backtest.py`に`BACKTEST_VARIANTS`環境変数を追加(デフォルトa/b/c全部、
   従来通り)。`BACKTEST_VARIANTS=b`でパターンbのみ実行でき、日次モデル再学習の対象が
   減る分だけ実行時間も短縮できる(全505日で約20分→パターンb単独で数分程度に短縮)。
   `backtest_conclusion.md`の上書きはa/b/c全部揃っている場合のみに限定し、b単独実行では
   スキップするようガードした(Phase4の確定済み結論を誤って壊さないため)。
2. `backtest.py`のパターンbスコアリングループに、predicted_probability>=0.70
   (Sランク閾値)のレースに限って6艇全員分の確率を`data/archive/analysis_outputs/backtest_full_probs_b.csv`
   に出力する処理を追加(全レース×6艇を残すと461,250行になり不要に大きいため、
   シミュレーション対象範囲にのみ絞った。日次モデル再学習のコスト自体はレースの
   絞り込みでは減らせないため、これは出力サイズのみの最適化)。
3. `scripts/tools/backfill_exotic_payouts.py`(新規)で、`data/archive/results_races.csv`の
   2連単/3連単/3連複払戻が空欄の日(505日)についてAPIを再取得し、既存行にマージして
   埋めた(`fetch_results.py`本体は日付が既存ならスキップする設計のため使えず、
   別スクリプトが必要だった)。
4. `scripts/analysis/simulate_s_rank_bets.py`(新規)で上記2つの出力を読み込み、
   `generate_bets.rank_for_probability`/`RANK_BUDGET`/`build_bets`と
   `evaluate_bets.evaluate_bet`を本番同様そのまま呼び出してシミュレーション。

5. `backtest.py`実行(数分)と`backfill_exotic_payouts.py`実行(505回API呼び出し、
   約8分)は互いに独立なファイルを扱うため並行実行した。

## ワークフローのpush競合対策(2026-09-18)

2026-09-18の`morning_program.yml`(scheduled #3、GitHubの遅延で10:08 JST実行)が
`git push`で「rejected (fetch first)」となり失敗した。原因は、同時刻帯に別のpush(Coworkの
候補選定Routineのclaude/*ブランチ→`auto_merge_data_branches.yml`によるmainへのfast-forward
等)が入り、ワークフロー開始時点のcheckoutより`main`が進んでいたこと。
`evening_results.yml`/`evening_results_retry.yml`も素の`git push`で同じ構造だが、Actionsの
実行履歴(evening #1〜#4、retry #1〜#3)はすべて成功で、実際に失敗したのはmorning #3のみ
(evening系は投稿時刻がRoutineのpushと重なりにくいだけで、構造上は同じリスクを持つ)。

対応: `scripts/git_push_with_retry.sh`を新設(`git pull --rebase origin main && git push`、
最大3回、リベース衝突時は`git rebase --abort`して再試行、全滅したら非ゼロ終了)し、3つの
ワークフローで使用。eveningの2本は、`generate_bets.py`が書き換えたcandidates.json
(evaluate_bets.pyで使用済みの一時的なもの)が未コミットのまま作業ツリーに残ると
`pull --rebase`が拒否されるため、push前に`git checkout --`で破棄する。bareリポジトリ2つで
「素のpushは拒否され、スクリプトはrebaseして成功する」ことをローカル確認済み。

## 締切直前の通知メール(2026-09-19追加)

`deadline_reminder.yml`(5分おき)が`scripts/deadline_reminder.py`を呼び、候補レースの締切まで残り
約5〜12分になったレースを1件ずつ短いメールで通知する(推奨買い目を再掲)。外部サイトへのアクセスは
無く、`data/latest/candidates.json`・programsの`race_closed_at`・predictionsとサーバー現在時刻だけで判定する。

設計判断:
- **通知範囲は依頼の「10〜12分前」ではなく「5〜12分前」にした**。cronは5分おきなので、幅3分の窓では
  どのtickにも当たらず通知が出ないレースが約4割出る。幅7分(5〜12分)ならどのレースも必ず1回は窓に入る。
  実際の通知は最初に窓へ入ったtickで、残り約7〜12分前になる。窓は`WINDOW_MIN/MAX_MINUTES`で変更可能。
- **GitHub Actionsのcronは5分間隔でも遅延・間引きがありうる**(9/17〜18のevening/morningは実際に
  数時間遅延した)。遅延で窓を通り過ぎたレースは通知されない(直前すぎる古い通知は出さない方針)。
  確実性が要るなら外部cron(cron-job.org等)から`workflow_dispatch`を叩く構成が別案。
- 時刻はすべてJST。cronはUTC指定のため`2-59/5 23`(=JST8時台)と`2-59/5 0-12`(=JST9〜21時台)の2本で
  JST8:02〜21:57を覆う。分を2,7,12,...にしたのは毎時0分ちょうどのGitHub側混雑(evening系で数時間遅延)を避けるため。
  `race_closed_at`はタイムゾーン無しのJST壁時計時刻で、スクリプトは現在時刻を`common.JST`に変換してから比較する。
- 送信済み管理は`data/latest/deadline_reminders_sent.json`(日付ごとにリセット)をコミットして持つ。
  「記録をpush→メール送信」の順のため、pushに失敗した回は送信せず次のtickで再判定する。逆に、記録後に
  SMTP送信だけ失敗するとそのレースは再送されない(重複より取りこぼしを許容)。
- テスト用に`workflow_dispatch`の`simulate_now`(JST時刻)で任意の時刻を「現在」として判定でき、その場合は
  送信済み記録を更新せず件名に【テスト】が付く。

## 締切直前オッズの取得・蓄積(2026-09-19追加、`odds_fetch.yml` / `scripts/fetch_odds.py`)

目的: 買い目配分が予測確率のみで実オッズを見ていないことが回収率頭打ちの原因なので、まず「締切10分前の
実オッズ」を貯める。**オッズを使った買い目・掛け金の補正、夜メールへの朝/直前の並記、差分の考察レポートは
今回のスコープ外**(データが貯まってから設計を相談して決める)。

確認したこと(実装前に実ページで確認):
- `https://www.boatrace.jp/robots.txt` は `User-agent: *` / `Disallow:`(空)で全許可。
- 使うのはログイン不要の一般公開ページ `race/odds2tf`(2連単+2連複)・`odds3t`・`odds3f`(`rno`/`jcd`(2桁)/`hd`(YYYYMMDD))。
  UTF-8。`h3.title7_title`の見出し直後の`div.table1`内tableに、通常セルの`td.oddsPoint`がオッズ。
  2連系は「相手艇番+オッズ」の2列/グループ、3連系は「2番目の艇番(rowspan)+3番目の艇番+オッズ」の3列/グループで、
  存在しない組み合わせは`is-disabled`。rowspanを展開してグリッド化して読む(標準ライブラリのHTMLParserのみ、新規依存なし)。
- パースの検証: 1レースで2連単30/2連複15/3連単120/3連複20件(全通り・重複なし)、各賭式で`Σ1/オッズ`が約1.34
  (=払戻率75%の逆数)。さらに2026-09-17 第8場2Rで、結果の払戻(2連単1-2=2.0倍、3連単1-2-4=10.6倍、3連複
  1=2=4=8.4倍)がページのオッズと完全一致。

設計判断:
- 単勝・複勝は取らない(`generate_bets.py`が使う3賭式に合わせた)。1レース=3ページ×1回。
- User-Agentは"boatrace-predictor-personal-tool/1.0"と名乗る。ランダム待機・ヘッダー偽装はしない。
  403/429は即停止(リトライ無し、exit 1で失敗扱い。それまでに取れたCSVはコミット)、404は「未公開」として
  今回スキップ(次回再試行)、タイムアウト等のみ最大2回リトライ(固定3秒)。動作はモックで確認済み。
- 対象はcaution降格後のランクがSS/S/A(SSは「S以上」として含めた)。締切の5〜15分前(「10分前±5分」)に入った
  レースだけ。5分おき起動なら幅10分の窓に必ず1回は入る。窓を過ぎてしまった(cron遅延等)レースは取得しない。
- 出力は `data/latest/odds/{YYYY-MM-DD}_{場}_{R}.csv`(long形式、`fetched_at,race_date,stadium_number,race_number,
  race_closed_at,bet_type,combination,odds`、combination表記は買い目・結果CSVと同じ`1-2-3`/`1=2=3`)。
  ファイルの有無が取得済みフラグ。1レース約185行・約15KB、1日数〜十数レース想定。**日次で増え続ける**ので、
  肥大化したら`data/archive/`へ移す(`candidates_evaluations.csv`と同じ扱い)。
- cronは依頼の`*/5 * * * *`から、JST 8:04〜21:59に絞り、分を4,9,14…にずらした(深夜の空振り防止と、毎時0分の
  GitHub側混雑=数時間遅延の実績を避けるため。`deadline_reminder.yml`の2,7,12…ともずらした)。
- 時刻はzoneinfoのAsia/Tokyo(依頼どおり)。Windowsにはtzdataが無いため`requirements.txt`に`tzdata`を追加、
  ワークフローでも`pip install tzdata`する。
- 既知の制約: GitHubのcronは遅延・間引きがありうる(9/17〜18に実例)。取得できなかったレースは欠測になる。

## EVティア方式の実装(2026-09-23、`generate_bets.py`/`deadline_reminder.py`/新規スクリプト2本)

別セッションで実施した過去60日間(2026-07-19〜09-17、2,397レース)の確定オッズ分析に
基づき、3連単に限定したEVベースの賭け金ルールを実装した。

**結論の再掲**:
- 3連単で「EV(Harville確率×最終オッズ)が2.0以上の買い目だけに絞る」のが最良
  (60日シミュレーションで554レース・総賭け金294万3,000円・総払戻426万300円・
  回収率144.8%・損益+131万7,300円)。
- 賭け金はランクではなくEVの大きさで段階的に変える: EV<2.0は0円/EV[2.0,3.0)は3,000円/
  EV>=3.0は6,000円。
- 2連単に同じ方式を適用すると回収率60.3%の大赤字だったため、EVティア方式は**3連単のみ**
  に適用する(2連単は長期オッズで確率推定が甘くなる=フェイバリット・ロングショット・
  バイアス的な傾向が確認されている)。
- **これらの数字はすべてこの60日間限定のチューニング値**。境界値(2.0/3.0)・金額
  (3,000/6,000円)はこの期間のデータに合わせたものであり、データが増えたら定期的に
  見直す前提(自動でしきい値・金額を書き換える仕組みは作らない。見直すかどうかは
  蓄積データ(`data/latest/ev_tier_evaluations.csv`)を見ながら人と相談して決める)。

**2段構え設計(重要)**: EVの計算にはオッズが必要で、オッズが揃うのは締切5〜15分前
(`fetch_odds.py`)。そのため、朝の候補選定(`generate_bets.py`のメイン処理=
`candidates.json`への書き込み)は一切変更していない(ランク基準のbudget/betsは
引き続き「仮の目安」として朝のメールに残る)。EVベースの確定金額は、オッズが揃う
締切直前に`deadline_reminder.py`側で別途計算して表示する。`generate_bets.py`に追加した
`ev_tier_budget()`/`load_odds_for_race()`/`trifecta_ev_by_combo()`/`ev_tier_bets()`/
`attach_ev_to_bets()`はいずれも**メモリ上の計算のみ**で、`candidates.json`には書き込まない。

**実装内容**:
1. `generate_bets.py`: 上記の関数群を追加(定数`EV_TIER_THRESHOLDS`/`EV_TIER_BET_TYPE`は
   ファイル冒頭にまとめ、後から調整しやすくした)。
2. `deadline_reminder.py`: 締切直前メールに、(a)既存のランク基準bets各行への
   EV・目安金額の付記(3連単かつオッズが取れている場合のみ、`attach_ev_to_bets()`経由。
   `build_candidates_email.format_bet_line()`にオプション表示として実装、朝のメールは
   オッズが無いため表示は変わらない)と、(b)全120通りの3連単組み合わせをEVで評価した
   「EVティア判定」セクション(`ev_tier_bets()`、EV>=2.0の組み合わせを◎付きでEV降順表示、
   無ければ「見送り目安」と明示)を追加。オッズ未取得のレースは「オッズ未取得のため
   計算できません」と表示してフォールバックする(`odds_fetch.yml`と`deadline_reminder.yml`の
   タイミングのズレは既知のため)。**自動で買い目を除外・追加することはしない**
   (判断材料を見せるだけ、という既存方針を維持)。既存の「※オッズは考慮していません」の
   注記は、オッズ有無で出し分けるよう修正した。
3. `scripts/check_odds_accuracy.py`(新規、`evening_results.yml`/`_retry.yml`に組み込み、
   人手不要): 締切直前オッズのスナップショット(`data/latest/odds/`)と結果確定後の
   実際の払戻を突き合わせ、`data/latest/odds_accuracy.csv`に日次蓄積する。**制約**:
   全組み合わせの最終オッズは日次では持っていない(手動バックフィル専用の
   `backfill_odds.py`系でしか取得していない)ため、比較できるのは「その回の実際の
   的中組み合わせについて、締切直前スナップショットのオッズ」対「確定payoutから
   逆算した最終オッズ(payout/100)」に限定される。集計・グラフ化はスコープ外(データを
   溜める仕組みのみ)。
4. `scripts/evaluate_ev_tier.py`(新規、同じく`evening_results.yml`/`_retry.yml`に組み込み):
   EVティア方式(3.のEV計算+`ev_tier_bets()`)をその日の候補レース(オッズ取得済みの
   ものに限る)に適用したら実際どうだったかを`data/latest/ev_tier_evaluations.csv`に
   蓄積する(EV>=2.0の組み合わせごとに1行、無い場合は「見送り」として1行、
   `bets_evaluations.csv`と同じ「1行=1買い目、追記」方針)。**方針の切り分け**:
   結果は自動で記録・蓄積し続けるが、しきい値・金額を変えるかどうかは、このデータを
   見ながら人と相談して決める(自動調整の仕組みは作らない)。
5. `scripts/tools/check_odds_manual.py`(新規、手動実行専用・完全にオプション): 人が
   見たオッズと自動取得オッズを比較し、差(既定20%以上)があれば警告する。
   `--stadium`/`--race`/`--combo`/`--observed_odds`を渡す。どちらのオッズを使うかは
   表示するだけで、何も自動で書き換えない。タスク1〜3とは独立して動作し、使わなくても
   他の機能に影響しない。

**設計判断の理由**:
- 「朝のbetsを直接EVで絞り込む」のではなく「別セクションでEVティア判定を並記する」形に
  したのは、(a)朝の時点ではオッズが無くEV自体が計算できないこと、(b)分析で分かった
  「EV>=2.0の組み合わせは、必ずしも朝のランク基準で選ばれた買い目と一致しない」
  (Aランクが多い等)ことを踏まえ、既存のランク基準の買い目提案を壊さずに、EVという
  独立した判断軸を追加情報として見せる方が「自動で除外・見送りはしない、判断材料を
  見せるだけ」という既存の設計思想(`BETTING_NOTE`)に合致するため。
- `evaluate_ev_tier.py`の対象を「オッズ取得済みの候補レースのみ」に限定したのは、
  `odds_fetch.yml`自体がSS/S/A候補のみを対象にしているため(B/Cランクや対象外の
  レースはそもそもオッズが無くEVを計算できない)。B/Cランクのオッズ取得は別課題
  (STATUS.md「4.3 B/Cランクレースのオッズ取得」参照、現状保留中)。

### スコープ訂正: EV計算の対象を全120通り→上位8点に制限(2026-09-23)

実装直後の2026-09-23、三国3Rの実運用判定で「EV>=2.0の買い目が5点・合計18,000円
(ランク予算5,000円の3.6倍)」になるケースが発覚。当初は「1レースあたりの上限額を
設けるべきか」という議論になったが、`定義は崩さない、逃げたら負ける/回収率で考えて
いる以上ぶれたらおかしくなる`という判断で上限は設けず、そのままpush・mainへマージ
した(この判断自体は撤回しない。以下は別の問題)。

その後、「そもそもEVの参加定義が過去に決めた話とずれていないか」という疑問が
あらためて出た。`data/archive/odds_backfill_60days.csv`(元の60日間バックテストで
実際に使われた買い目データ)を集計したところ、以下が判明した:

- 1レースあたりの買い目点数は中央値5点・最大8点(全120通りではない)。
  分布: 2点35レース/3点57/4点271/5点1,736/7点242/8点94(計2,435レース)。
- 1着に指定されている艇は1号艇が2,435件中2,435件…ではなく、1号艇2,435/2号艇290/
  3号艇288/4号艇137/5号艇25と、1号艇(本命)に大きく偏っている
  (集計コマンド: `awk -F, 'NR>1{split($4,a,"-"); print $1,$2,$3,a[1]}' 
  data/archive/odds_backfill_60days.csv | sort | uniq -c | awk '{print $NF}' | sort | uniq -c`)。

つまり元の60日間バックテストは、3連単の全120通りではなく、当時の候補選定ロジックが
出していた(本命寄りの)買い目リストを母集団にしていた可能性が高い。一方、実装した
`trifecta_ev_by_combo()`は`trifecta_ordered_combos()`経由で全120通りを対象にEVを
計算していたため、**バックテストで検証していない範囲(1着が下位艇の高オッズ組み合わせ
等)まで賭けてしまう**、母集団のずれ(scope creep)があったと判断した。

**注意**: これは100%確証があるわけではない。この60日間バックテスト(EVティア方式、
2026-09-21〜22に別セッションで実施)がどのスクリプト・どの候補選定ロジックで
買い目リストを生成したのか、その元データ・元スクリプトがこのリポジトリにコミット
されておらず特定できていないため、厳密な再現・再検証はできない。あくまで
`data/archive/odds_backfill_60days.csv`(実際に使われた買い目データそのもの)の
分布から読み取れる状況証拠からの推定(2026-09-23確認時点)。

なお、当初の下書きでは「元データ`sa_rank_downgraded_bets.csv`が未コミットのまま
消失」としていたが、2026-09-23にユーザーの指摘でリポジトリ全履歴を検索した結果、
そのファイル名は一度も存在しないことが判明し、事実誤認と分かったため上記の通り
表現を訂正した(類似名の`data/archive/s_rank_simulation_bets.csv`は別のSランク
全賭けシミュレーション用のデータで、現在も正常にコミットされており消失していない。
STATUS.mdの該当バックログ項目も削除済み)。

**対応**: `trifecta_ev_by_combo()`にHarville確率上位`EV_TIER_MAX_CANDIDATES`(=8)点
までに絞るフィルタを追加(`generate_bets.py`)。8は上記分布の最大値に合わせた値。
既存のランク基準ロジックがそもそも「確率上位N点を選ぶ」という同じ考え方を使っている
ため、設計として大きな逸脱ではない。しきい値・金額と同様、この8という値も暫定値
であり、`data/latest/ev_tier_evaluations.csv`の蓄積データを見ながら見直すこと
(自動調整の仕組みは無い、という既存方針は変えない)。

`attach_ev_to_bets()`(朝のランク基準betsへのEV付記)は元々ランク基準ロジックが
選んだ買い目だけを対象にしており、この訂正の影響を受けない。`ev_tier_bets()`
(締切直前メールの「EVティア判定」セクション、`evaluate_ev_tier.py`の実績記録)は
どちらも`trifecta_ev_by_combo()`経由なので、この訂正が自動的に反映される。

## メール未送信の不具合(2026-09-17、Stage 1稼働直後に発覚)

`evening_results.yml`/`evening_results_retry.yml`実行後、候補振り返り・収支P&Lの
メール2通が両方ともスキップされた。原因は「重複送信防止マーカー」ではなく、
**日付のズレ**だった:

- `fetch_results.py`は引数省略時「昨日」(`today_jst()-1`)の結果を取得する設計
  (`evaluate.py`/`train_model.py`の日次再学習も同じく「昨日」基準で、これ自体は
  元々の一貫した設計であり問題ない)。
- 一方`data/latest/candidates.json`は毎朝「当日」の日付で上書きされる(アーカイブされない)。
- そのため夜間ジョブが当日22:00/23:00 JSTに走っても、`results_races.csv`には
  「当日」の行がまだ無く、`evaluate_candidates.py`/`evaluate_bets.py`が
  「結果データがまだありません」で正常終了(exit 0)しつつ何も出力しない
  → レポート.txtが存在しない → `hashFiles(...)`条件が偽 → メール送信ステップが
  スキップされる、という流れだった。

**修正**: 両ワークフローに、モデル再学習用の「昨日」取得とは別に、
`python fetch_results.py "$(TZ=Asia/Tokyo date +%Y-%m-%d)"`で明示的に「当日(JST)」
の結果も取得するステップを追加(`evaluate_candidates.py`の直前)。ローカルで
2026-09-17分を実際に取得し、`evaluate_candidates.py`/`generate_bets.py`/
`evaluate_bets.py`が正常に完走してレポートを生成することを確認済み
(ローカルで取得したデータはCI側の実行を正とするため`git checkout`で破棄し、
コミットはワークフロー修正のみ)。
